# Security Review — Hostel Management System

This document summarizes security measures implemented and verified for the final-year project (Chapter 5/6 reference).

## Authentication & Authorization

| Check | Implementation |
|-------|----------------|
| Password hashing | bcrypt via Laravel's `Hash` facade and `'password' => 'hashed'` cast on User model |
| Role-based access | Spatie `laravel-permission` + `EnsureUserHasRole` middleware on all `/student/*`, `/warden/*`, `/caretaker/*`, `/admin/*` routes |
| Cross-role URL access | Redirects to user's own dashboard with flash message (not raw 403) |
| Account deactivation | `is_active` flag checked at login; inactive users cannot authenticate |
| Session security | Laravel database sessions with CSRF protection enabled |

## Input Validation

All form submissions use dedicated Form Request classes:

- `StudentRegisterRequest` — email domain, student ID uniqueness
- `StoreBookingRequest` — room existence and availability
- `InitiatePaymentRequest` — phone number format
- `RejectBookingRequest` — rejection reason required
- `StoreMaintenanceRequest` — category enum, description length, photo mime/size
- `StoreUserRequest` — admin user creation validation

Client-side validation is supplementary only; server-side rules are authoritative.

## OWASP Top 10 Coverage

### A01 — Broken Access Control
- Middleware enforces role on every protected route
- Booking/payment actions verify ownership (`authorizeBooking()`)
- Admin-only user management endpoints

### A02 — Cryptographic Failures
- Passwords never stored in plain text
- M-Pesa credentials in `.env` only (never committed)
- HTTPS recommended for production callback URLs

### A03 — Injection
- Eloquent ORM with parameterized queries throughout
- No raw SQL with user input
- Form Request validation on all inputs

### A04 — Insecure Design
- Booking race condition handled with pessimistic locking (`lockForUpdate()`)
- Payment callback wrapped in try/catch to prevent flow breakage

### A05 — Security Misconfiguration
- `.env` excluded from git via `.gitignore`
- Debug mode (`APP_DEBUG`) should be `false` in production
- Default demo passwords documented for development only

### A06 — Vulnerable Components
- Dependencies managed via Composer with locked versions
- Run `composer audit` before deployment

### A07 — Authentication Failures
- Rate limiting on login via `LoginRequest`
- Remember-me uses secure Laravel tokens

### A08 — Software & Data Integrity
- CSRF tokens on all POST/PATCH/DELETE forms (Laravel default)
- M-Pesa callback validates `CheckoutRequestID` against stored payment

### A09 — Logging & Monitoring
- M-Pesa callbacks logged via `Log::info` / `Log::error`
- Notification failures logged to `notifications_log` table

### A10 — SSRF
- Outbound HTTP limited to configured M-Pesa API base URL
- No user-controlled URL fetching

## XSS Prevention

- Blade `{{ }}` escaping used for all user-generated output
- No `{!! !!}` on user input

## File Upload

- Maintenance photos restricted to image mime types
- Stored in `storage/app/public/maintenance/` via Laravel's filesystem
- File names generated by Laravel (not user-supplied)

## Known Limitations (Academic Project Scope)

- No two-factor authentication
- SMS notifications stubbed (Africa's Talking interface ready, no live credentials)
- M-Pesa callback URL requires ngrok/tunnel for local sandbox testing
- No rate limiting on booking submission (would add in production)
- Session fixation protection relies on Laravel defaults

## Recommended Production Hardening

1. Set `APP_DEBUG=false`
2. Use HTTPS with valid TLS certificate
3. Configure real mail/SMS providers
4. Add rate limiting on auth and payment endpoints
5. Enable Laravel's `TrustProxies` for load balancer deployment
6. Regular `composer audit` and dependency updates
